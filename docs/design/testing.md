# Testing

Testing GUI code is harder than testing most libraries. The code needs a display, an event loop, and, on macOS, the process's main thread. This document describes how WxKit's tests run anyway.

## Kinds of tests

WxKit has three kinds of tests:

- Managed API tests, in `tests/WxKit.Tests`. These create real windows and check lifetime, events, threading, strings, and the rest of the managed API against real wxWidgets.
- A Native AOT smoke test, in `scripts/test-aot.ps1`. It publishes each sample, the Hello sample and the text editor, with Native AOT, checks that nothing ships beside the executable, and on macOS that the app bundle is valid and signed, and runs it in a mode that shows its window, waits for the event loop to start, and exits. This catches link problems that no other test can.
- Generator tests, in `tests/WxKit.Generator.Tests`, once the generator exists. These check that the generator turns sample Doxygen XML into the expected output. They are plain unit tests with no GUI, and they run anywhere.

To run the first two:

```powershell
dotnet test --project tests/WxKit.Tests
./scripts/test-aot.ps1
```

## The main thread problem

Test frameworks run tests on worker threads. wxWidgets needs every GUI call on one thread, and on macOS that thread must be the process's main thread, so a test cannot simply create a frame.

The tests use xUnit v3, whose test projects are executables. `WxKit.Tests` turns off xUnit's generated entry point with `XunitAutoGeneratedEntryPoint` and has its own `Main`, in `Program.cs`. It calls `Application.Run`, which takes the main thread for wxWidgets, and starts xUnit's runner on a thread of its own. It picks the runner the same way xUnit's generated entry point does: Microsoft.Testing.Platform when it is started with `--server`, which is how `dotnet test` starts it, and xUnit's console runner otherwise, such as under `dotnet run`. When the runner finishes, it ends the event loop with `Application.Exit`, so a test that leaks a window cannot keep the run from ending.

Each test hands its body to the GUI thread through the `Gui` helper:

- `Gui.Run` posts the body to the GUI thread, waits for it, and returns its result. The body can be async, and its continuations stay on the GUI thread.
- `Gui.WithFrame` runs the body with a new frame, and destroys the frame afterwards if the body did not.
- `Gui.WaitUntil` lets the event loop run until a condition holds, for things wxWidgets does at idle time, such as destroying a top-level window.
- An exception that escapes an event handler while a body runs fails the test, since nothing else would report it. A test that expects one takes it with `Gui.TakeUnhandled`.

A hidden frame stays open for the whole run, because the event loop ends when the last top-level window is destroyed. Tests do not run in parallel, as `xunit.runner.json` sets, because they share the one GUI thread.

The .NET 10 SDK runs `dotnet test` through Microsoft.Testing.Platform only for repositories that opt in, which `global.json` does.

## Using controls from tests

Some events only come from the user, such as a button click. On Windows, the tests send the window messages that the user's action would send, with `SendMessage`, which processes them before it returns, events included. A click is sent as the `WM_COMMAND` notification the button sends its parent, because `BM_CLICK` only works on a button in the active window. These tests skip themselves on other platforms, until each platform has an equivalent.

## Displays in CI

- Windows runners have a desktop, so tests run as they are.
- macOS runners have a window server, so tests run as they are.
- Linux runners have no display. Tests run under `xvfb-run`, which provides a virtual X server, with GTK set to use X11.
- On a Windows machine, WSL runs the Linux tests, and WSLg gives GTK a display.

## Tests for one platform

Some tests only mean something on Windows: those that click a control or choose a menu item by sending it the Windows message the click would, and those that read a control through MSAA, as a Windows screen reader does. Elsewhere they skip, with `Assert.SkipUnless`, so a skipped count is expected on Linux.

The other tests run everywhere, so they avoid what only one platform does. Windows paints a window during `Update`, for example, and GTK on its next frame once the window is shown, so a test of painting waits for the paint while the event loop runs.

## What tests avoid

- Tests do not depend on the pixel layout of native controls, which differs between platforms, themes, and DPI settings.
- Tests do not show modal dialogs, which would block the run. Dialog code is tested by creating dialogs and inspecting them without calling `ShowModal`.
- A hung test must not hold a runner for hours. Each `Gui.Run` gives up after 10 seconds, and the CI job has a timeout of its own.

## Accessibility checks

Native controls are accessible by default, but the way an application builds them can still break that, such as creating a label after the control it names. The Hello sample was checked by hand through MSAA, where its text box is named after the label before it and its button reports its role and state.

The tests of `Accessible` read a window through MSAA, as a screen reader does. `Msaa.Of` asks Windows for the window's `IAccessible`, which in the same process and on the GUI thread is the window's own, so a test can ask for a name, role, state, or child count and check what the control's `Accessible` answered. Making checks like that for the Hello sample's controls is a later step.

When checking from .NET, note that the managed UI Automation client in `System.Windows.Automation` reports every Win32 control as a pane with no patterns, because it lacks the client-side providers that map them. MSAA, or the native UI Automation COM interface, shows the real roles and names, as a screen reader sees them.
